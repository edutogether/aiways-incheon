# 구글 계정 인증 — 검토했다가 폐기 (2026-09-09)

**결론: 폐기.** 학교마다 구글 계정 상황이 제각각이라(발급 안 된 학교, 발급됐는데
모르는 학교, 옛날 계정 학교, 최신 세팅 학교) **이메일 도메인으로 학교를 판별한다는
설계의 전제 자체가 성립하지 않는다.** Bumm님 판단으로 시연 후 과제로도 두지 않는다.

나중에 교육청 계정 체계가 통일되면 이 문서부터 다시 보면 된다.

## 무엇을 하려던 것이었나

학생 구글 계정 도메인이 학교마다 일정하다면(`dongbang.els.gclass.co.kr` 같은 형태),
**이메일 도메인만 보고 학교를 자동 판별**할 수 있다. 그러면 지금 가입에서 손이 가장
많이 가는 "학교 검색해서 고르기" 단계가 통째로 사라진다.

## 조사에서 확인한 것 (나중에 다시 볼 때 유용한 사실들)

### 지금 구조가 구글 로그인을 명시적으로 거부한다

`functions/lib/edu2gDeviceAccess.js`의 `authenticate()`:

```js
if (decoded?.firebase?.sign_in_provider !== "anonymous") return failure("anonymous_auth_required", 403);
```

**익명이 아닌 모든 로그인이 20개 보호 엔드포인트 전부에서 403으로 막힌다.** 한 줄이지만,
이건 "구글 로그인을 추가하는 일"이 아니라 **인증 모델을 교체하는 일**임을 보여준다.

### 신원의 근거가 기기에서 계정으로 옮겨간다

| | 지금 | 구글 로그인 |
|---|---|---|
| 신원의 근거 | **기기**(익명 세션 + `edu2gDeviceBindings`) | **계정**(이메일) |
| 기기를 바꾸면 | 다른 사람이 됨 — 기록이 안 따라감 | 로그인하면 그대로 이어짐 |
| 같은 기기를 여럿이 쓰면 | 구분 불가 | 로그아웃/로그인으로 구분 |

지금의 "기기 영구 고정"은 **번호 도용을 막는 장치**이기도 하다(다른 학생이 내 번호로
가입하려 해도 자기 기기엔 이미 자기 actor가 붙어 있다). 계정 기반이 되면 그 보호가
사라지는 대신 **이메일이 그 역할을 더 강하게 한다**(한 계정 = 한 학생).

### 도메인으로 알 수 있는 것은 학교까지다

학년·반은 이메일에서 신뢰성 있게 읽을 수 없다(학교마다 계정 규칙이 다르다). 그래서
**학교 검색 단계만 사라지고, 학년·반·번호·이름은 여전히 입력**해야 한다.
`DASHBOARD_LAUNCHED_SCHOOLS` 하드코딩이 도메인 매핑표로 바뀌는 것뿐이다.

### 도메인 제한은 서버에서 해야 한다

클라이언트의 `hd` 파라미터는 힌트일 뿐 우회 가능하다. **실제 강제는 서버에서**
`verifyIdToken` 결과의 `email` 도메인과 `email_verified`를 함께 확인해야 하고, 그 자리는
위 `sign_in_provider` 검사가 있는 곳이다. (Firebase 콘솔의 "승인된 도메인"은 앱이
호스팅되는 주소를 뜻하는 다른 개념이다.)

### 가장 큰 현실적 제약 — 초등학생이 로그인할 수 있는가

파일럿에 **1학년(서흥초)**이 포함돼 있다. 구글 로그인은 아이디·비밀번호 입력이 필요하고,
기기를 바꾸거나 로그아웃되면 다시 로그인해야 하며, 공용 태블릿이면 매번 로그인/로그아웃이
필요하다. **지금 익명 방식의 가장 큰 장점이 "학생이 아무것도 안 해도 된다"는 것**이라,
이걸 잃는 비용이 얻는 것보다 큰지는 교실 현실을 아는 사람만 판단할 수 있다.

## 다시 검토한다면 먼저 확인할 것

1. 네 학교의 **실제** 학생 계정 도메인 (통일됐는지)
2. 선생님과 학생의 도메인이 **다른지** — 같으면 교사코드가 계속 필요하다
3. 초등 저학년이 실제로 로그인 가능한 환경인지(개인 기기인지 공용인지, 비밀번호를 아는지)
4. 기존 익명 사용자 데이터를 어떻게 이관할지 — `actorId = uid`라 단순 병합이 안 된다
