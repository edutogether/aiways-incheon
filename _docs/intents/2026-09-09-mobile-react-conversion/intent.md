# mobile/ 을 React + TypeScript 로 전환한다 — 화면과 체감을 그대로 둔 채로

## 문제

`mobile/`은 실제 초등학생이 매일 쓰는 화면인데 구조가 이렇다:

- `mobile/index.html` 456줄에 4개 탭·모달 3종의 DOM이 **전부 정적으로** 박혀 있고,
- `mobile/app.js` 1,274줄짜리 IIFE 하나가 `getElementById`로 그 DOM을 직접 붙잡아
  보이고/숨기고/글자를 갈아끼운다. 상태(실천 통계, 보류함, 퀴즈 진행, 가입 정보)는
  모듈 스코프의 `let` 변수 6개이고, 그 변수와 화면을 맞추는 일은 `updateStatsUI()`
  같은 함수를 **부르는 것을 잊지 않는 것**으로만 보장된다.

이 구조의 실제 비용은 두 가지다. 하나는 **한 곳을 고치면 다른 곳이 조용히 어긋나는
것**이고(상태와 화면을 잇는 강제 장치가 없다), 다른 하나는 **타입이 없어 서버
응답의 필드 이름이 바뀌어도 실행하기 전엔 모른다**는 것이다.

조직 차원의 이유도 있다. 8개 앱 중 Portal·Voice Cinema·CLASSCADE·Be a Googler·
Codyssey가 이미 React+TS이고 Poster Studio도 전환 중이라, 이 저장소만 남으면
사람이 앱을 옮겨 다닐 때마다 다른 관례를 다시 익혀야 한다.

## 원하는 결과

`mobile/`이 React 18 + TypeScript(strict)로 다시 쓰여 있고, **그 화면이 지금 화면과
측정값 수준에서 같다**. 구체적으로, 전환이 끝난 뒤 아래가 성립해야 한다:

1. `tests/baseline`을 지금 고정된 스냅샷 그대로 돌렸을 때 **4개 뷰포트 × 4개 탭 ×
   (semantics·motion·layout·스크린샷) 전부 통과**한다. 스냅샷을 새로 찍어서 맞추는
   것이 아니라, **전환 전에 찍힌 파일을 그대로 두고** 통과해야 한다.
2. 상호작용 상태(모달 열림, 퀴즈 정·오답, 보류함 목록, 검색 자동완성, 가입 폼
   역할 전환)도 같은 방식으로 고정돼 있고 통과한다 — 아래 "증명 방법" 참고.
3. `mobile/tailwind.generated.css`와 `mobile/mobile.css`가 **바이트 단위로 같다.**
   즉 스타일시트를 다시 만들지 않는다.
4. 서버와 주고받는 요청/응답에 타입이 붙어 있고, `tsc --noEmit`이 통과한다.
5. 배포 산출물이 지금과 같은 경로(`/mobile/index.html`)로 서비스되고,
   `_hosting_site` 화이트리스트 원칙(소스가 배포에 섞이지 않음)이 유지된다.

## 증명 방법 (이 작업의 핵심 — 착수 전에 정해 둔다)

"같다"는 주장은 눈대중이 아니라 **전환 전에 찍어 둔 파일과의 차이 없음**으로만
한다. 기준선 하네스(`tests/baseline/mobileBaseline.spec.js`)가 이미 세 가지를 뜬다:

| 덤프 | 무엇을 잡는가 | 왜 따로 있는가 |
|---|---|---|
| `layout` | 정지 상태의 박스·폰트·색·간격 | 모양이 틀어진 것 |
| `motion` | transition/animation의 **선언값**(duration·easing·delay) | "모양은 같은데 움직임이 달라진" 회귀 |
| `semantics` | id 집합·meta·alt·aria·링크·입력 속성 | 화면에 안 보여서 픽셀 대조로는 절대 안 잡히는 유실 |

`semantics`가 특히 중요한 이유: 이 앱은 `getElementById`로 DOM을 직접 붙잡는
구조라 **id 하나가 사라지면 그 기능이 조용히 죽는다.** 다른 저장소(Voice Cinema)가
전환 과정에서 요소 id 21개를 잃고도 픽셀·스타일 대조를 전부 통과한 전례가 있다.
현재 `mobile/index.html`의 id 110개가 스냅샷의 110개와 정확히 일치한다.

**지금 하네스로는 부족한 부분이 있고, 그걸 먼저 메운다.** 하네스는 각 탭의 **첫
화면**만 뜬다. 그래서 아래는 아직 어떤 스냅샷에도 안 잡혀 있다:

- 판단 결과 모달(`#judgeModal`) 열린 상태 — 품목별 결과 렌더링
- 공용 확인 모달(`#customModal`), 시각 알림(`showVisualAlert`)
- 퀴즈 정답/오답 직후 상태, 마지막 문제 후 결과 화면
- 보류함에 항목이 있을 때의 목록
- 검색 자동완성 목록이 뜬 상태
- 가입 폼의 학생/담임 역할 전환, 담임 인사 문구

이 상태들은 HTML에 요소는 있지만 `display:none`이라, 지금 `layout` 덤프에 찍히는
값은 **숨겨진 상태의 값**이다. 전환 후 열린 모습이 달라져도 안 잡힌다. 그래서
**코드를 한 줄도 옮기기 전에 이 상태들까지 기준선에 넣는다**(아래 S0).

## 단계 (각 단계마다 되돌려서 실패하는지 확인한다)

되돌려서 실패하는지 확인한다 = 새로 추가한 검증이 **실제로 회귀를 잡는지**를,
일부러 값을 틀리게 만들어 빨간불이 뜨는 것으로 확인한다. 통과하는 것만 보면
"아무것도 검사하지 않는 테스트"와 구별되지 않는다.

- **S0 — 기준선 확장.** 위에 적은 상호작용 상태를 하네스에 추가하고 스냅샷을
  찍는다. 제품 코드는 한 줄도 안 건드린다. 되돌림 확인: 예컨대 모달의
  `border-radius`를 임시로 바꿔 해당 스냅샷만 빨개지는 것을 본다.
- **S1 — 토대.** `mobile-app/`에 React+TS+Vite 프로젝트를 만든다(루트가 아니라
  하위 폴더인 이유는 아래 제약 참고). 이 단계의 산출물은 `mobile-next/`로 나가고
  **라이브 `mobile/`은 건드리지 않는다.** 하네스가 두 경로를 같은 검사로 대조한다.
- **S2 — 마크업.** `index.html` → TSX 컴포넌트. class 문자열을 **그대로 옮긴다**
  (Tailwind를 다시 만들지 않으므로 클래스 이름이 곧 스타일이다). 로직 없음.
  이 시점에 `semantics`·`layout` 정지 대조가 통과해야 한다.
- **S3 — 데이터·순수 로직.** `sortingData`/`sortingVision`/`sortingTextTip`를 타입
  붙인 TS 모듈로. 서버 응답 타입을 여기서 정의한다.
- **S4 — 상태와 상호작용.** 탭·퀴즈·보류함·통계·가입·랭킹을 훅으로. S0에서 넓힌
  상호작용 스냅샷이 여기서 전부 통과해야 한다.
- **S5 — 교체.** 인증 게이트 통합, `mobile/`을 빌드 산출물로 바꾸고 손으로 쓴
  파일을 지운다. 배포 파이프라인에 빌드 단계를 넣는다. 라이브가 바뀌는 것은
  **이 단계 하나뿐이다.**

## 영향받는 사용자·시스템

- **실사용자: 있다.** 파일럿 4개 학교의 초등학생 전원이 매일 쓰는 화면이다.
  S5 전까지는 라이브가 바뀌지 않지만, S5는 곧 전면 교체다.
- **연결된 것**: 상위 폴더의 `firebaseAppCheck.js` / `firebaseBetaAuth.js` /
  `edu2gBetaClient.js`는 **PC 앱과 공유**한다. 이 셋은 이번 작업에서 건드리지
  않고, React 앱도 지금처럼 전역(`window.AIWays*`)으로 읽는다.
- **배포**: `scripts/stageHostingSite.js`(화이트리스트)와 `.github/workflows/deploy.yml`이
  S5에서 바뀐다. `firebase.json`의 `hosting.public`은 그대로다.

## 제약

- **UI/UX가 지금과 "체감까지" 같아야 한다.** 애니메이션 길이·이징·스크롤 느낌·
  타이밍 포함. "언어를 바꿨으니 이렇게밖에 안 된다 / 누더기를 뜯다 보니 /
  일단 이렇게 하고 나중에 / 차선책으로" — 넷 다 금지다. 지킬 수 없다는 걸
  발견하면 완화하지 말고 **멈추고 묻는다.**
- **PC 화면(`index.html`/`style.css`/`styles/`/루트 `app.js`)은 건드리지 않는다.**
  Bumm님 직접관리 영역이다. 전환 대상은 `mobile/`뿐이다.
- **`mobile/tailwind.generated.css`를 다시 만들지 않는다.** 24KB짜리 사전 생성
  번들이 커밋돼 있고 빌드 파이프라인이 없다. 다시 만들면 purge 범위·Tailwind
  버전 차이로 화면이 미세하게 달라질 수 있는데, 그 차이는 "체감까지 동일"을
  깨뜨리면서도 발견하기는 어렵다. **그대로 쓴다.**
- **루트 `package.json`에 `"type": "module"`을 넣지 않는다.** 루트 `.js`들은
  브라우저가 `<script>`로 읽는 고전 스크립트이고 `functions/test`의 여러 테스트가
  그걸 `require()`한다 — 실제로 이것 때문에 CI가 한 번 깨졌다. 그래서 React
  프로젝트는 **자기 `package.json`을 가진 `mobile-app/` 하위 폴더**에 둔다.
- **`_hosting_site` 화이트리스트 모델을 유지한다.** 소스가 배포에 섞이면 안 된다
  (GitHub Pages 시절 저장소 전체가 공개된 사고의 재발 방지 장치다).
- **되돌릴 수 있어야 한다.** S5 직전까지 라이브는 손대지 않고, S5는 한 커밋으로
  묶어 `git revert` 하나로 돌아갈 수 있게 한다.
- **마감이 있다.** 9/13 제출, 9/17 시연. S1~S4가 라이브를 안 건드리므로, 어느
  단계에서 멈춰도 제출물은 지금 동작하는 화면 그대로다.

## 미결 질문

- **S5를 마감 전에 할 것인가, 후에 할 것인가.** S1~S4는 라이브에 무해하지만 S5는
  전면 교체다. 9/13 제출·9/17 시연 전에 넘길지, 시연을 지금 코드로 치르고 그
  뒤에 넘길지는 제가 정할 일이 아니다. **S4까지 마치고 다시 여쭙는다.**
- 네이버 동료평가가 저장소를 본다면, 전환 중간 상태(`mobile/`과 `mobile-app/`이
  공존)가 어떻게 읽힐지. 평가 시점과 전환 진도가 겹치면 S5를 앞당길 이유가 된다.
