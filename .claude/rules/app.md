## 도메인 (2026-09-09 확정·완료)

이 앱의 정식 주소는 **`https://incheon.edutogether.kr`**다(Firebase 주소를 노출하지 않기 위함).
처음엔 `aiways.edutogether.kr`로 잡았다가 가비아에서 `incheon`으로 확정됐다 — **`aiways`는 DNS에
존재하지 않으니 어디에도 남기지 말 것**(허용목록에 미리 넣었다가 실제로 틀린 이름이었던 적이 있다).

**Firebase Hosting은 커스텀 도메인을 "추가"하는 것이지 기본 도메인을 대체하지 않는다** — 그래서
`ai-ways-incheon.web.app`과 `.firebaseapp.com`도 페이지 자체는 계속 뜬다. **끌 수 있는 수단이 없다.**

**`web.app`을 하루 만에 뺐다가 다시 넣었다. 경위를 남긴다 — 다음 사람이 반드시 묻는다.**

- **2026-09-09에 뺐다**: 박람회 때 쓰던 사용자를 정리하고 4학교 클로즈베타로 다시 시작하려고.
  그 주소로 들어오면 화면은 떠도 API가 전부 `invalid_origin`으로 거부되는 상태였다.
- **2026-09-10에 다시 넣었다**: 이유는 클로즈베타가 아니라 **가용성**이다. 그날 정식 주소에서
  App Check 토큰을 못 받아 아무 기능도 안 되는 일이 실제로 벌어졌는데, **그때 들어갈 다른 길이
  하나도 없었다.** Bumm님 판단 — 현 주소가 안 되면 대비용으로 쓸 수 있어야 한다.

🔴 **오리진을 다시 연 것이 클로즈베타 정리를 되돌린 것은 아니다.** 누가 쓸 수 있는지는 오리진이
아니라 **교사코드·가입** 쪽에서 강제된다. 두 가지를 섞어서 판단하지 말 것.

(`firebaseapp.com`은 Firebase Auth가 쓰는 도메인이라 처음부터 그대로 둔다.)

배포 후 스모크(`scripts/postDeploySmoke.js`)가 **두 주소 모두** 실제로 통하는지 확인한다 —
대비용이 정작 필요할 때 안 되면 대비가 아니다.

**도메인이 붙은 것만으로는 부족하다** — 2026-09-09에 실제로 겪었다. 새 도메인은 정적 파일과 보안
헤더는 정상인데 **Functions 호출이 전부 `invalid_origin` 403**이었다(CORS 허용목록 미갱신). 정적
파일 해시만 비교해서는 이 층이 안 보인다. **배포 후 `scripts/postDeploySmoke.js`가 실제 오리진으로
API를 두드려 보는 것이 이 층을 확인하는 유일한 방법이다.**

**남은 미확인**: 새 도메인에서 App Check가 실사용자에게 통하는지는 **실제 휴대폰으로만** 확인된다
(자동화 브라우저는 승인 여부와 무관하게 항상 403 — 아래 함정 참고).

## 공유 카드(og:image) — 앱마다 다른 카드가 의도된 상태다 (2026-09-10)

PC 대표 주소(`index.html`)는 **포털이 만든 카드**를 쓴다
(`assets/og/incheon.jpg`, 1200×630). 포털이 6개 앱의 카드를 sha256으로 감시하며,
🔴 **바이트 그대로 복사해 자기 도메인에서 서빙한다** — 포털 주소를 가리키면
포털이 죽을 때 6개 앱의 카드가 같이 죽고, 다시 인코딩하면 감시 검사가 계속
불일치로 잡는다. **webp로 바꾸지 않는다(카카오톡이 썸네일로 못 쓴다).**

🔴 **모바일(`mobile/index.html`)은 자기 카드(`mobile-og-thumbnail.jpg`)를
그대로 쓴다. 포털 카드와 통일하지 않는다 — 의도된 상태다.** 포털 카드는
"AI Ways Incheon이라는 프로젝트"를 소개하는 그림이고, 모바일 링크를 받는
사람은 **학생이 직접 쓰는 앱**으로 들어간다. 다른 것을 여는 링크에는 다른
카드가 맞다. 포털 검사도 각 앱의 대표 주소 하나씩만 본다.

🔴 **이미지뿐 아니라 문구(`og:title`/`og:description`/`twitter:*`)도 모바일은 따로
간다 — 의도된 것이다**(2026-09-10 확인). PC는 포털 정본(`portal/src/data/apps.ts`의
`hook`/`full`)에 맞췄지만, 포털에 이 앱 항목은 **PC 대표 주소 하나뿐**이라 모바일은
그 대상이 아니다. 모바일 링크를 받는 사람은 **학생이 직접 쓰는 앱**으로 들어가므로
"우리 학교의 자원순환 현황을 확인하고"(교사 대시보드 설명)가 맞지 않는다.
**다르다고 해서 맞추지 말 것.**

출처가 맞다는 독립적인 증거다.

학급 수는 해마다 바뀐다. 새 학년도가 되면 그 스크립트를 다시 돌린다.

행사 대상 학년 값은 `app.js`의 `SCHOOL_CLASS_CONFIG`에도 있고(학생 반 선택 화면),
관리자 화면의 학년·반 고르기는 `schoolClassCounts.js`를 쓴다.
🔴 **이미 여러 차례 답을 받은 값이다. 세션이 또 확인 요청하지 않는다** — 추정으로
채우는 것이 위험한 것이지, 이 값 자체는 확정이다. 값이 틀리면 있는 반이 목록에서
빠져 **그 반 선생님이 아예 못 들어간다.**

## 교사 인증코드 규칙 (2026-09-09 확정)

코드는 **`<학교영문><학년><반두자리>`** 형식이고 **전부 대문자**다 — 예: `DONGBANG502`(동방초 5학년 2반).
예전에는 임의 코드를 발급했는데 서버엔 scrypt 해시로만 남아 **발급한 사람이 종이에 적어두지 않으면
다시 볼 수 없었다.** 규칙으로 파생시키면 그 번거로움이 사라진다(`admin.html`이 학교·학년·반을
넣는 즉시 자동으로 채워준다).

**학교 영문 표기 — 국어의 로마자 표기법 기준**:

| 학교 | 표기 |
|---|---|
| 인천서흥초 | `SEOHEUNG` |
| 인천청라초 | **`CHEONGNA`** |
| 인천동방초 | `DONGBANG` |
| 인천마전초 | `MAJEON` |

🔴 **청라는 `CHEONGRA`가 아니라 `CHEONGNA`다.** 오타로 보여서 고치고 싶어지는 자리라 근거를 남긴다 —
로마자 표기법은 글자가 아니라 **발음**을 옮기는데, 청라는 ㅇ 받침 뒤 ㄹ이 ㄴ으로 바뀌어 **[청나]**로
소리난다. **인천시 공식 표기도 `Cheongna`**(Cheongna International City)이고, **학교 홈페이지
도메인도 `cheongna.icees.kr`**이다. 나머지 셋은 발음 변화가 없어 표기가 그대로다.

**학교가 홈페이지에 쓰는 자체 표기와 다를 수는 있다.** 다만 이 코드는 운영자가 발급하고 담임이
입력하는 내부 값이지 학교의 공식 영문명을 쓰는 자리가 아니라, 표기법 기준으로 통일한다.

**한 반은 코드를 여러 개 받는다(2026-09-09 Bumm님 결정 — 대체가 아니라 공존).**
다른 반 선생님들은 규칙 코드(`SEOHEUNG103`)를 쓰고, 아래 네 분은 개인 코드를 쓰는데
**둘 다 통한다.** 대체로 만들면 개인 코드에 문제가 생겼을 때 그 선생님이 들어갈 길이
하나도 없어진다.

| 선생님 | 반 | 개인 코드 |
|---|---|---|
| 박상현 | 서흥초 1-3 | `EDU2G SANGHYUN` |
| 진가연 | 청라초 3-4 | `EDU2G GAYEON` |
| 강서희 | 동방초 5-1 | `EDU2G SEOHEE` |
| 이혜련 | 마전초 6-3 | `EDU2G HYERYEON` |

발급은 `admin.html`에서 **"기존 코드를 두고 추가로 등록"** 을 체크하고 넣는다. 서버는
대표 코드가 없는 반에는 추가를 거부한다(규칙 코드를 먼저 발급해야 한다). 한 반에 추가
코드는 3개까지 — 검증할 때마다 등록된 수만큼 scrypt를 돌리기 때문이다.

🔴 **코드 비교는 공백을 전부 지우고 대문자로 맞춘 뒤에 한다.** `edu2g sanghyun`,
`EDU2GSANGHYUN`, 공백 두 개 전부 통과한다. 이게 없으면 띄어쓰기 하나 때문에 실패가
쌓여 **그 반 전체가 15분 잠긴다**(10분에 10회 실패 시 반 단위 잠금) — 수업 시간에
그 반 선생님이 아예 못 들어가는 사고가 된다.

**코드를 주는 사람의 호칭은 "운영자"다** — 앱 안에 이미 "선생님"과 "슈퍼어드민"이 있어
"관리자"는 그 둘 다로 읽히고, "개발자"는 담임 입장에서 왜 그 사람이 코드를 주는지 설명이 안 된다.

## 마감 절차 — 데이터 전면 삭제 (2026-09-09 Bumm님 예약 지시)

**지금 하지 말 것.** 테스트하는 동안 익명 계정은 계속 생기고, 대표님이 아직 어드민으로
둘러보며 확인하시는 중이다.

**시점**: 대표님이 **어드민으로 직접 둘러보시며 확신이 선 뒤** · 최종 배포 후 ·
**freeze 태그를 찍기 직전**. "이제 100점이고 배포하고 정기감사만 기다리자" 하는 그 자리.

**대상 — 둘 다 지운다**:
- Firebase Authentication의 **익명 계정 전부**(2026-09-09 기준 472개, 계속 증가 중)
- **Firestore 데이터** — `actors/{actorId}`의 학생 프로필·기록, `studentNumberClaims`의 번호 점유,
  `schools/.../students`의 개인랭킹 문서

🔴 **둘을 반드시 함께 지워야 한다.** 이 앱은 `actorId`가 곧 uid라(익명 세션에 actor를 자동

**주의**:

## `uuid` 취약점 — 올리지 않기로 한 것과, 그 판단이 무너지는 조건 (2026-09-10)

Dependabot 경보 1건(`uuid`, GHSA-w5hq-g745-h8pq, CVSS 7.5, **runtime**)을 **올리지
않기로 확정했다**(팀장 경유 결정). 근거와 함께 전제를 남긴다 — 다음 감사에서
**결론이 아니라 이 전제부터** 확인한다(§4-1-1).

**근거**: 취약한 것은 `v3()`/`v5()`/`v6()`에 **caller가 준 출력 버퍼를 넘길 때**의
경계검사 누락이다. 그런데 이 저장소에서 `uuid`는 **직접 의존성이 아니고**
(`functions/` 소스는 한 줄도 안 쓴다) `gaxios`(`^9.0.1`)와 `teeny-request`(`^9.0.0`)가
물고 있는데, 둘이 실제로 부르는 것은 이것뿐이다:

```
gaxios/build/src/gaxios.js:417        const boundary = (0, uuid_1.v4)();
teeny-request/build/src/index.js:135  const boundary = uuid.v4();
```

**`v4()`이고 버퍼를 안 넘긴다 — 취약 함수에 닿지 않는다.** 패치본 `11.1.1`은 두
라이브러리의 `^9` 제약 때문에 `overrides` 강제나 Google 클라이언트 스택
(gaxios/google-auth-library/firebase-admin) 전체 상향이 필요하다. **닿지 않는
취약점 때문에 실제 학생이 쓰는 백엔드의 런타임 의존성을 흔드는 것은 맞바꿈이
나쁘다.**

🔴 **이 판단이 무너지는 조건 둘. 둘 중 하나라도 참이면 실제 취약점이 된다:**
1. **`functions/` 코드가 `uuid`를 직접 쓰기 시작한다** — 특히 `v3`/`v5`/`v6`.
2. **`gaxios`/`teeny-request`가 `v3`/`v5`/`v6`를 버퍼와 함께 쓰도록 바뀐다**
   (두 패키지를 올린 뒤에는 위 두 줄을 다시 확인해야 한다).

## 모바일 기준선은 **탭을 한 바퀴 돈 뒤**에 잰다 (2026-09-11)

`useSharedTabHeight`의 공유 탭 높이는 **본 적 있는 탭 중 가장 큰 값**이고
**커지기만 한다.** 그래서 값을 정하는 것은 "언제 재느냐"가 아니라 **"그때까지
어느 탭을 봤느냐"**다. 거기에 앱이 마운트 뒤 **400ms·1200ms에 스스로 다시 잰다**
(웹폰트가 늦게 오면 줄바꿈이 달라지므로).

그 둘이 엇갈리면서 기준선이 실행마다 흔들렸다 — 30 / 28 / 22 통과처럼 매번
달랐다. 🔴 **`workers: 1`이라 병렬 문제가 아니었다.** 하네스에서 기다리는 시점을
네 가지로 바꿔 봤지만 전부 흔들렸다.

**해결: `openApp`이 탭을 한 바퀴 돌아 높이를 수렴시킨 뒤에 잰다.** 그러면 순서에
의존하는 구조 자체가 사라진다. 근거는 실측이다 — **실제 학생도 탭을 몇 번
옮기면 같은 최종값(1275px)에 도달한다.** 수렴 상태는 잘 정의된 하나의 상태이고,
예전 기준선이 담고 있던 값은 **성장 곡선 위의 임의의 한 점**(경합 결과)이었다.

그래서 2026-09-11에 기준선을 다시 찍었다. 🔴 **바뀐 것은 `height`와 `_box`뿐이고
`semantics`·`motion`은 한 글자도 안 바뀌었다** — 구조·id·aria·모션 명세는 그대로다.
스크린샷이 같이 바뀐 것은 **카드가 수렴 높이만큼 길어진 것** 하나로 설명된다.

## 학생 앱의 인증 게이트는 **앱을 가리지 않는다** (2026-09-10 변경)

예전에는 `checkStudentProfile()` 왕복이 끝날 때까지 앱을 통째로 가려 뒀다. 대표님이
실제 폰에서 **"모바일 스플래시가 다섯 번 지나간다"**(막대 주기 1.1s × 5 ≈ 5.5초)고
하셔서 재보니:

- **앱은 2초에 이미 다 그려져 있었다**(요소 368개). `display:none`으로 가려져만 있었다
- 기다리던 시간의 정체는 **`DOMContentLoaded` 3.9초 → 토큰을 처음 "요청"한 시각 9.7초**.
  그 5.8초는 **Firebase SDK 285KB + reCAPTCHA Enterprise 2.5MB를 내려받아 초기화**하는

  학생도 그 시간은 똑같이 낸다

**App Check 토큰은 서버를 부를 때 필요한 것이지 화면을 그릴 때 필요한 것이 아니다.**
그래서 화면은 바로 보여주고 탐침은 뒤에서 돌린다. 실측 262ms(제한 없음)~4.0초(3G).

🔴 **실패를 알리는 방식이 이 변경의 핵심 위험이다.** 사라지는 토스트로 하면 학생이
못 보고 지나쳐 **"저장이 안 되는 상태인 줄 모른 채" 사진을 찍는다.** 이 앱은 App Check가
한 번 거부되면 그 기기가 **24시간 계속 실패**하므로 그 상태가 오래 간다. 그래서:

- 실패하면 **화면 맨 위에 계속 남는 띠**로 알린다(`#authGate`를 띠로 바꿔 재활용한다 —

- **저장·분석을 실제로 누르면 그 자리에서 또 막히고 이유가 나온다**(원래 있던 경로다)

### 🔴 실패 상태에서 사진을 찍으면 그 사진은 안 남는다 — **이 변경 탓이 아니다**

인증 확인이 실패한 상태에서 사진을 넣으면: 스캔 모달이 열렸다가(1.2초) 닫히고(7초)
**"연결을 다시 확인해 주세요."** 토스트가 뜨며, 사진 버튼은 다시 눌린다. **조용히
실패하지 않는다.** 다만 **찍은 사진은 안 남는다** — `onPhotoSelected`가

비운다(같은 사진을 연달아 고를 수 있게 하려는 원본 동작).

**잃는 것의 크기**: 서버에는 아무것도 안 갔으므로 잃는 것은 **다시 찍는 수고**다(카메라라
몇 초). 그동안 화면 맨 위 띠가 계속 "저장·분석이 안 됩니다"를 말하고 있다.

### 🔴 "띠가 뜬 동안 사진·저장 버튼을 비활성으로" — 검토했고 하지 않기로 했다

지금은 **"눌러 보면 알 수 있는" 상태**이고, 잃는 것은 다시 찍는 수고뿐이며, 띠가 이미

## 지시를 한 파일의 문제로 좁혀 읽지 않는다 (2026-09-10)

PC 전환 S4에서 팀장 지시는 **"언제 실행되는가에 기대지 말고 누가 호출하는가로
바꾼다"**였다. 세션은 그것을 **`app.js` 한 파일의 문제로 좁혀 읽고** `app.js`만
배선했다. 그런데 **같은 구조의 고전 스크립트가 열 개**였고, 그중 둘
(`responsiveNavigation.js`·`deviceTier.js`)이 똑같이 "실행되는 순간 DOM을 잡고,
못 찾으면 조용히 `return`"이었다. 둘 다 전환본에서 아무 일도 안 하고 있었다.

🔴 **조용히 `return`하는 코드는 고장 신호를 안 낸다.** 콘솔에도 안 남고 화면에도
"안 됨"이 안 보이며, 그 기능이 원래 없었던 것처럼 보인다.

**그래서 지시를 받으면 그 성질을 가진 것이 몇 개인지부터 센다.** "이 파일을
고치라"가 아니라 **"이 성질을 가진 것을 고치라"**로 읽는다. S4에서 그렇게 했으면
세 개를 한 번에 봤을 것이고, 실제로는 S5 합격 판정을 미리 돌려서야 나왔다.

설치·실행 단계가 없다. 루트 `npm test`(`build:mobile && playwright test`)는 **로컬 전용**이다.

**의도적으로 뺀 것이 아니라 그냥 빠져 있다** — 다른 저장소처럼 "리눅스 러너에 기준 이미지가 없어서"
같은 근거가 주석으로도 없다. CI에서 화면을 지키는 것은 `functions/test/frontend*.test.js` 넷(DOM
계약·배치 계약·CSS 구조·디자인 시스템)인데, 소스 수준 단언이라 **이번 태블릿 같은 비례 문제는

`reactShell.spec.js`(스크립트 순서·tailwind 해시)는 픽셀과 무관해 리눅스에서도 돌 수 있다 —
CI에 넣을 후보다(아직 안 넣었다).

## 스플래시는 **자기 애니메이션 두 바퀴**가 하한이다 (2026-09-11, COMMON_STANDARDS §27)

Bumm님이 PC 화면에서 **"스플래시가 안 보일 정도로 스쳐 지나간다"**고 하셨다. 재보니
**0.1~0.9초**였다. 모바일에는 이미 하한이 있었는데(`authGate.js`의 `MINIMUM_TURNS = 2`)
**PC에는 없었다.**

🔴 **한쪽에 넣은 하한은 다른 쪽에 가지 않는다. 기기마다 따로 넣고 따로 잰다.**
이번 건이 정확히 그 사례다 — 모바일에만 넣어 두고 PC는 하한이 없는 채로 몇 주를 보냈다.

- **하한은 "몇 초"가 아니라 "자기 애니메이션 두 바퀴"다.** `getAnimations()`로 실제
  주기를 읽어 계산하므로 **막대 주기를 바꾸면 하한이 따라온다.** 못 읽으면 현재
  주기(PC 1.15s / 모바일 1.1s)로 셈한다.
- **상한(5초)은 그대로다.** 하한과 상한은 목적이 달라 따로 정한다 — 상한은 부팅이
  실패해도 화면이 갇히지 않게 하는 장치다. 두 바퀴(2.3초)가 5초보다 짧아 부딪히지 않는다.
- **자료를 기다려 더 오래 뜨는 것은 하한과 무관하다.** 학교가 설정돼 있으면
  `deferSplashHide`로 자료 도착까지 기다려 3.5초가 나온다. **하한은 기다릴 자료가
  없을 때의 바닥**이다.

### 🔴 태블릿은 PC와 **같은 스플래시**를 탄다 — 따로 넣을 것이 없다

실측으로 확인했다(2026-09-11). `#bootSplash`를 끄는 CSS가 태블릿 구간에 없고,
768×1024에서 **2,681ms**, 1180×820에서 **2,660ms**가 나온다 — PC(2,676ms)와 같다.
**PC를 고치면 태블릿도 같이 고쳐진다.**

### 🔴 PC 스플래시를 고치면 **CSP 해시를 같이 갱신해야 한다**

그 인라인 스크립트는 `firebase.json`의 `script-src`에 **sha256 해시로** 허용된다.
한 글자만 바꿔도 해시가 어긋나고 **브라우저가 조용히 막아** 스플래시가 5초 타임아웃
전까지 안 걷힌다. `scripts/checkMiniappCsp.js`가 배포 전에 잡는다 — 이번에도 실제로
잡아서 멈춰 세웠다.

🔴 **사본이 둘이다**: `index.html`과 `pc-app/index.html`(전환본). **바이트까지 같아야**
해시 하나로 둘 다 덮인다. 고칠 때 **둘을 같이** 고치고, 같은지 확인한다.

### 🔴 학교 모달은 **스플래시가 걷히기 시작할 때** 연다 — top-layer가 스플래시를 덮는다

`<dialog>.showModal()`은 **네이티브 top-layer**라 스플래시의 `z-index:9999`로는 **절대 못
이긴다.** 예전에는 첫 방문(학교 미설정)에서 모달이 **64ms에 열려 스플래시를 통째로
덮었고**, 사용자가 실제로 본 스플래시는 **29ms뿐**이었다. 화면에는 "어두운 배경 + 흰
모달"만 보이고 대시보드는 2.8초 뒤 스플래시가 걷힐 때 블러 뒤로 뒤늦게 나타났다 —
Bumm님이 **"메인이 2초 죽었다가 뒤늦게 나온다"**고 하신 것이 이것이다. **그 어두운
배경이 죽은 화면이 아니라 스플래시였다.**

**사양(2026-09-11 Bumm님)**: ①스플래시 두 바퀴 → ②걷히면서 **메인과 모달이 함께 등장**
(메인은 뒤에서 블러) → ③모달을 닫거나 학교를 고르면 메인이 밝아진다.

`app.js`의 `afterBootSplashStartsFading()`이 그 순서를 만든다. **다 걷힌 뒤가 아니라
페이드를 시작하는 순간**에 열어야 "함께 등장"이 된다 — 다 걷힌 뒤에 열면 대시보드만
보였다가 모달이 튀어나온다. 🔴 스플래시가 어떤 이유로도 안 걷히면 **모달이 영영 안
열려 학교를 고를 방법이 사라지므로**, 상한(5초)보다 넉넉한 7초 뒤에는 그냥 연다.

실제 첫 방문에서는 스플래시가 29ms만 보였다. **요소가 보이는 것과 사용자가 보는 것은
다르다** — 지금은 `elementFromPoint`로 **화면 한가운데에 실제로 무엇이 있는지**를 같이 본다.

`tests/splashFloor.spec.js`가 **상수를 읽지 않고 화면에 실제로 보인 시간을 잰다**
(PC·태블릿 두 방향·학생 앱 + 상한). 🔴 재는 조건이 중요하다 — **학교 미설정 ·
warm 캐시 · 스로틀 없음**. 설정돼 있으면 자료를 기다려 하한이 안 보이고, 느린
조건에서만 재면 하한이 없어도 통과한다(대표님 기계에서 0.1초가 나온 것이 그 경우다).
하한을 0으로 낮춰 **실제로 빨간불이 뜨는 것**까지 확인했다(PC 524ms · 학생앱 423ms).

## 학교 검색은 **브라우저 안에서** 돈다 — `searchSchool`은 폴백이다 (2026-09-11)

학교 검색이 타자마다 서버를 거쳐 느렸다(실측 **콜드 1.89초 / 웜 0.16초**). Bumm님
요구는 "타자 치는 대로 좁혀지는" 것이었고, **서버를 거치는 한 그건 나올 수 없다.**

그래서 **전국 학교 목록 12,672개**를 `assets/school-list.tsv`에 굳혔다. 검색은
브라우저에서 **0.4~1.5ms**에 끝난다. 부분 일치 · 띄어쓰기 무시 · **초성**(`ㅇㅊㅅㅎ`
→ 인천서흥…)까지 된다.

- **만드는 것은 `scripts/fetchSchoolList.js`**(`fetchSchoolClassCounts.js`와 같은 자리·방식).
  학년도가 바뀌거나 학교가 신설·개명되면 다시 돌린다. 받은 시각이 파일 첫머리에 있다.
  🔴 **NEIS 인증키는 Secret Manager의 `NEIS_API_KEY`에 있고, 실행 중 환경변수로만 쓴다.**
  저장소·로그·커밋에 남기지 않는다(스크립트가 URL조차 출력하지 않는다 — 쿼리에 키가 들어간다).
- **초성 색인은 파일에 굳히지 않고 브라우저에서 만든다** — 만드는 데 **4.6ms**,
  파일에 굳히면 **brotli +31.2KB**다. 5ms 벌자고 31KB를 더 받을 이유가 없다.
- **캐시**: `firebase.json`이 `/assets/school-list.tsv` **하나만** 1년 불변으로 준다.
  🔴 **`assets/**`로 넓히면 안 된다** — 그 안에 QR(`kiosk-5-1.png`)·로고·og 카드처럼
  **이름이 그대로인 채 내용만 바뀌는** 파일이 있고, 1년 불변을 주면 QR을 바꿔도 1년 동안
  옛 QR을 보는 사람이 생긴다. 내용이 바뀌면 `app.js`의 `?v=` 해시가 같이 바뀌어 주소가
  달라지므로 이 파일은 안전하다(스크립트가 둘을 **항상 같이** 고치고, 못 고치면 멈춘다).

### 🔴 `searchSchool` 함수를 지우지 않는다 — 이제 진짜 역할이 있다

예전 이유(export를 지우면 CI 배포가 안전장치로 멈춘다)에 더해, **목록이 아직 안
왔거나 못 받았을 때 그쪽으로 떨어진다.** 그래서 느린 회선·아낌 모드에서도 **지금보다
나빠지는 경우가 없다.**

🔴 **두 경로가 `renderSchoolResults()` 하나로 그린다.** 두 벌로 두면 한쪽만 고쳐지는
날이 오고, 그때 "폴백일 때만 화면이 다른" 상태가 된다. 서버 응답(`toSchool`)과 정적
행의 필드가 **완전히 같은 다섯**(`schoolCode`·`schoolName`·`schoolLevel`·`region`·
`address`)인 것을 실측으로 확인했다.

### 미리받기 조건 — 실측으로 지킨 것 셋

- **학생 앱은 받지 않는다.** `app.js`는 PC 대시보드에서만 실행된다(학생 앱은 `mobile/`

- **첫 화면을 늦추지 않는다.** `requestIdleCallback`(없으면 3초 뒤)로만 시작한다.

## 리액트 전환 (2026-09-09~, intent: `_docs/intents/2026-09-09-mobile-react-conversion/`)
- `mobile-app/`이 전환 프로젝트다. **루트 package.json에 `"type": "module"`을 넣지 않는다** — 루트 .js는 브라우저가 `<script>`로 읽는 고전 스크립트이고 functions/test가 `require()`한다(이것 때문에 CI가 한 번 죽었다). 그래서 하위 폴더에 자기 package.json을 뒀다
- **`mobile/tailwind.generated.css`를 다시 만들지 않는다.** 빌드 파이프라인 없이 만들어져 커밋된 24KB 사전 생성 번들이다. 다시 만들면 purge 범위·버전 차이로 화면이 미세하게 달라지는데 발견이 어렵다. 빌드가 바이트 그대로 복사하고, `reactShell.spec.js`가 해시를 대조한다
- **Vite가 넣는 번들 `<script type="module">`은 반드시 공유 스크립트 뒤에 와야 한다.** 앞에 오면 리액트가 `window.AIWaysEdu2gClient`보다 먼저 돌아 저장·로그인이 "가끔" 안 되는 형태로 깨진다 — 화면 스냅샷으로는 안 잡힌다. `vite.config.ts`의 `transformIndexHtml(order:"post")`가 순서를 잡고, `reactShell.spec.js`가 문서 순서를 검사한다
- 🔴 **`mobile/`은 더 이상 손으로 쓰는 폴더가 아니다. `mobile-app`의 빌드 산출물이고 git에 안 들어간다**(2026-09-09 S5). 소스는 `mobile-app/src`(화면·로직)와 `mobile-app/public`(빌드를 안 거치는 파일 - `authGate.js`, 스타일시트 둘). **`mobile/` 안의 파일을 고치면 다음 빌드에 지워진다**
- 배포 전에 반드시 `npm run build:mobile`. 잊으면 `scripts/stageHostingSite.js`가 "mobile/index.html 이 없습니다"로 멈춘다(조용히 빈 화면을 배포하지 않게 하는 장치다). CI는 `deploy-hosting`에서 직접 빌드한다
- 전환 전 원본(손으로 쓴 `mobile/` 전체)은 **`mobile-react-freeze-20260909`** 태그에 있다
- 🔴 **되돌릴 때도 CI 경로(`git revert` + push)를 쓴다. 로컬에서 `firebase deploy`로 되돌리지 않는다.** 윈도우 로컬 체크아웃은 CRLF, CI는 LF라 **내용이 같아도 파일 바이트가 달라진다**. 2026-09-09 롤백 예행연습에서 프리뷰 해시가 라이브와 달라 보여 잠깐 "되돌리기가 안 되는가" 했는데 줄끝 차이였다 — 정작 급하게 되돌려야 하는 순간에 이걸 처음 만나면 판단이 흔들린다

### 아직 안 한 것 (전환이 안정된 뒤 별건으로)
- **`authGate.js`는 옮기지 않았다.** App Check 실패 화면·재시도가 들어 있고 리액트 밖의 `#authGate`를 다시 그리는 구조라 성격이 다르다. 전환과 같이 건드리면 문제가 났을 때 원인 구분이 안 된다
- **후보 검증의 프로토타입 속성 통과**: `normalizeAnalysis`가 `db[itemId]`로만 확인해서 `itemId: "constructor"`가 통과한다(값이 함수라 truthy). 원본에 있던 성질이라 전환 중에는 고치지 않았다. 고칠 때는 `Object.hasOwn`으로 바꾸고 `sortingAnalysis.test.ts`의 해당 케이스도 같이 고친다

### 전환하면서 실제로 당한 것들 (같은 실수를 또 하지 않으려고 남긴다)
- **`{값}글자`로 쓰면 텍스트 노드가 둘로 쪼개지고 글자 폭이 소수점 아래에서 달라진다.** `현재 점수: {score}점`이 원본보다 0.03px 넓게 나왔다. 원본이 한 덩어리 문자열이면 전환본도 한 덩어리(`{`현재 점수: ${score}점`}`)로 써야 한다
- **JSX는 줄로 나뉜 요소 사이의 공백을 아예 없앤다.** 화면은 같아 보여도(flex `gap`이 간격을 만든다) `textContent`가 달라져서 스크린리더가 "❓잘 모르겠어요"처럼 붙여 읽는다. 원본이 `innerHTML` 템플릿이라 줄바꿈이 남는 자리에는 `{" "}`를 명시한다
- **같은 탭을 다시 눌러도 원본은 높이를 다시 잰다**(`switchTab`이 매번 `growSharedTabHeight`를 부른다). 활성 탭 값만 보고 `useEffect`를 걸면 값이 안 바뀌어 재측정을 건너뛴다
- **원본은 `classList.toggle`이라 클래스가 누적된다.** 담임 버튼은 `border-blue-200`이 계속 남은 채 `border-blue-600`이 더해지고, 테두리 색은 스타일시트 순서상 `border-blue-200`이 이긴다. "정리해서" 클래스를 통째로 갈아끼우면 **색이 바뀐다**
- **난수 시드를 고정해도 소비 순서가 다르면 결과가 다르다.** 원본은 이모지 회전이 먼저 난수를 쓰고 리액트는 첫 렌더에서 퀴즈를 먼저 뽑는다. 하네스가 시드를 되돌리고 "다시 도전하기"를 눌러 양쪽을 같은 자리에서 다시 뽑게 한다
- **같은 브라우저 컨텍스트에서 두 번째 페이지를 열면 익명 인증/App Check가 막힌다**(요청이 400으로 끝나고 응답이 안 온다). 원본과 전환본을 나란히 비교할 땐 **컨텍스트를 따로** 만든다. `browser.newContext()`에는 `playwright.config.js`의 `use` 설정이 안 붙으므로 `baseURL`을 직접 넘겨야 한다

## 검사가 실제로 무언가를 봤는지 (COMMON_STANDARDS §21)

이 저장소는 배포 판단이 사실상 시각회귀 대조 결과에 걸려 있어서, **"대상을 못
찾으면 조용히 통과"하는 검사**의 피해가 org에서 제일 크다. 2026-09-09에 전수로
훑어 6건을 고쳤고, 그때 배운 것:

- 🔴 **문지기가 감시 대상에서 기준을 가져오면 감시가 아니다.** 스모크 검사 개수를
  `PROD_ORIGINS.length * (functionNames.length + 1)`로 계산했더니, 목록을 비우면
  기대치도 같이 0이 되어 그대로 통과했다. **고정 하한으로 적어야 한다**
- **덤프가 빈 결과를 내면 "차이 없음"이 아니라 "화면이 안 떴다"는 뜻이다.**
  하한(`assertNotEmpty`)이 없으면 빈 스냅샷끼리 비교해 초록불이 나고, 더 나쁘게는
  그 빈 결과가 `--update-snapshots`로 기준선에 들어앉는다
- **`if (await x.count())` 로 감싸면 대상이 없을 때 조용히 건너뛴다.** 기준선이
  탭 버튼을 못 찾으면 직전 탭 화면을 그 탭의 정답으로 찍고 있었다
- **`filter(...).forEach(assert)` 는 걸러낸 게 0개면 단언이 통째로 사라진다.**
  거른 개수부터 못박는다
- **`existsSync`로 감싼 복사는 없는 것을 조용히 뺀다.** 배포 스테이징이 그랬다 -
  화면 파일이 통째로 사라져도 배포는 성공하고 빈 사이트가 나간다

## 🔴 CSP `img-src`에 `blob:`이 있어야 사진 분석이 돈다 (2026-09-11)

PC "AI 판단"과 학생 앱의 사진 분석은 `URL.createObjectURL(file)`이 만든 **`blob:` 주소**를
`<img>`에 넣고 `image.onload`에서 분석을 시작한다. `img-src`에 `blob:`이 없으면 브라우저가
막고 **`onload`가 영영 안 불려 분석이 시작조차 안 된다.** 서버에는 아무것도 가지 않으므로

## 자주 틀리는 것
- **App Check가 ENFORCED라 자동화 브라우저(Playwright 등)는 라이브에서 403 `App attestation failed`를 받는다. 이건 라이브 장애가 아니라 정상 동작이다.** reCAPTCHA Enterprise가 사람/봇 점수를 매기는데 자동화 브라우저는 `navigator.webdriver === true`라 낮은 점수를 받고 App Check가 그 토큰을 거부한다 — **헤드풀(`channel:"chrome"`)로 띄워도 똑같다. 헤드리스 여부가 아니라 자동화 여부가 감지된다.** 2026-09-09에 이 세션이 "라이브 다운"으로 오판해 보고했고, 같은 날 CLASSCADE도 같은 함정에 걸렸다. 라이브가 실제로 살아 있는지는 **사람이 실제 휴대폰으로 열어보는 것**이 유일하게 확실한 확인이다
- **자동화로 App Check를 확인하려는 시도는 이미 해봤고, 이 저장소에서는 안 된다**(2026-09-09 실측). 다른 저장소가 찾은 방법(헤드풀 실제 크롬으로 토큰을 받아 본문 없는 요청을 보내고, 응답 코드가 `app_check_*`인지 `auth_missing`인지로 가른다)을 그대로 옮겨 봤다. **서버 쪽 전제는 성립한다** — `protectedActor.js`가 App Check를 가장 먼저 보고 본문 파싱은 그 뒤라, 코드로 가를 수 있다. 그런데 **클라이언트 쪽에서 토큰 자체가 안 나온다**(헤드풀 크롬에서도 `getAIWaysAppCheckHeaders()`가 null). 🔴 **대조군(예전부터 등록된 `firebaseapp.com`)도 같이 막혔으므로 설정 문제가 아니라 자동화의 한계다.** 검사는 `tests/appCheckLiveProbe.spec.js`에 남겨 뒀다(기본은 건너뜀, `AIWAYS_APPCHECK_PROBE=1`로 실행). reCAPTCHA 설정이 바뀌면 저절로 통과하게 되고, **대조군만 통과하고 정식 주소가 막히면 그때는 실패로 알려준다**
- **자동화로 인증 이후 흐름을 보려면 디버그 토큰이 필요하고, 그건 localhost에서만 켜진다.** `firebaseAppCheck.js`의 `debugMode()`는 hostname이 `localhost`/`127.0.0.1`이고 쿼리에 `appcheck-debug=1`이 있을 때만 참이다(라이브 주소에서는 절대 안 켜진다). 그 상태로 열면 콘솔에 새 UUID가 찍히는데, **그 UUID를 Firebase 콘솔 > App Check > 앱 > 디버그 토큰 관리에 등록해야** 통과한다. Playwright는 실행마다 새 프로필이라 UUID가 매번 바뀌므로, 고정 토큰을 쓰려면 `?appcheck-debug=1` 없이 `addInitScript`로 `self.FIREBASE_APPCHECK_DEBUG_TOKEN = "<등록한 UUID>"`를 앱 스크립트보다 먼저 심는다(쿼리를 주면 코드가 `= true`로 덮어써서 매번 새로 생성된다). **등록된 디버그 토큰은 App Check를 우회하는 값이라 저장소에 커밋하지 않는다**

- **`functions/package.json`의 `check`는 하드코딩 목록이다.** 새 파일을 추가하고 여기 안 넣으면 문법 게이트에서 조용히 빠진다. eslint는 `functions/` 안만 보므로 루트 `.js`는 어느 게이트에도 안 걸린다 — 2026-09-07 감사에서 실제로 9개가 빠져 있었다
- **새 에뮬레이터 테스트는 네 군데에 등록해야 한다**: `vitest.emulator.config.js`의 `include`(빠지면 "No test files found") / `eslint.config.js`의 globals 오버라이드(빠지면 `'test' is not defined`) / `functions/package.json`(`check` + 새 `emulator:test:*` 스크립트) / `.github/workflows/deploy.yml` 스텝
- **에뮬레이터 테스트는 파일당 별도 프로세스로 격리한다** — 여러 파일이 같은 `teacherCodes` 문서 ID나 같은 `cb5_actor_*` 매트릭스를 써서 한 프로세스에 몰면 문서 경합으로 깨진다
- **무거운 테스트의 타임아웃은 실측으로 정한다** — 기본 20초인데 `cb5RecordResolveRecoveryEmulatorIntegration.js`만 실측 1분 26초라 파일 안에서 개별 타임아웃을 준다. 추측으로 늘리지 말 것
- **`saveSortingRecord`/`listSortingRecords`/`resolveSortingRecord`/`checkStudentProfile` 네 개는 일부러 `emulatorAppCheck`에서 빠져 있다** — 스모크 테스트가 실제 App Check 강제를 검증하기 때문이다. "일관성이 없어 보인다"고 우회를 추가하면 CI가 깨진다(실제로 한 번 깨뜨렸다)
- **레이트리밋이 전역/액터별 두 층이다.** 테스트에 가짜 시계를 주입할 땐 두 리미터와 대상 핸들러 **전부**에 같은 시계를 넣어야 한다 — 하나라도 실제 시계면 엉뚱한 리미터에 먼저 걸려 정작 검증하려던 로직에 도달하지 못한다
- **`transaction.set(ref, data, { merge: false })`는 문서를 통째로 갈아엎는다** — 나열 안 한 `status`/`plan`이 날아가 기기가 영구 잠긴 사고가 있었다. 필드 몇 개만 지우려면 `{ merge: true }` + `FieldValue.delete()`
- **폴링 주기를 줄일 땐 반드시 `perMinute`/`perDay` 상한과 같이 계산한다** — 계산 없이 줄였다가 등교시간에 켠 대시보드가 점심 전에 조용히 멈춘 장애가 있었다
- **실패한 CI를 그냥 재실행하지 않는다** — `gh run view --log-failed`로 원인부터 확인한다
- **배포는 push가 아니라 `success`를 눈으로 확인해야 끝난 것이다.** push 직후 "배포 중"이라고 보고하지 말고 `gh run list --branch main --limit 1`로 결과를 확인한 뒤 보고한다. 2026-09-09 하루에만 같은 유형이 두 번 났다 — ①긴급 CORS 수정을 push한 직후 문서 커밋을 밀어 넣어 **대기 중이던 그 배포가 취소**됐고(이 워크플로는 새 실행이 오면 대기 중 실행을 취소한다), ②승인 게이트 제거와 교사 관리 기능 두 커밋이 **연속으로 실패**했는데 세션은 "배포 중"으로 알고 시연 시나리오 작업으로 넘어가려 했다. 둘 다 팀장이 직접 CI를 확인해서 드러났다
- **긴급 수정을 push했으면 그 배포가 끝날 때까지 다른 것을 push하지 않는다** — 위 ①이 정확히 그 사고다

  안 나간 줄 모른다.** 9/9이 정확히 그랬다 — 취소 직후 세 실행이 **연속 failure**여서
